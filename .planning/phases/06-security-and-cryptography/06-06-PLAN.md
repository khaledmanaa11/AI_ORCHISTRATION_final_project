# Phase 6 Plan 6: Gap closure — peer-fault containment and sender validation

Closes `deferred-items.md` items 3 and 4, both verified by hand during 06-05 before being
logged. Neither is a §10.4 gate criterion; both are real exposures before league play.

## Item 3 is the more serious one, and it is not "just" a crash

`deadline.py` re-raises `ToolError` on purpose — an application-level rejection is not a
transport failure and must never be retried. That decision is right. The defect is that
**nothing above it catches the exception**, so the process dies by traceback at the worst
possible moment: `commit_own_action` has already written `{state, move, intent, nonce}` to our
ledger, and no FINAL_REVEAL has been sent. We become the side that published no nonces — a
rule-36 failure caused by *their* code.

The fix therefore does not touch `deadline.py`. It catches the exception where the game can
still end properly, and routes it into the pathway that already exists for "the peer failed
us", which ends the turn loop, writes `game_over`, and lets the Final-Reveal audit run.

## Why item 4's rejection is safe to add here but would not have been before

Rejecting a spoofed `sender` means raising `ToolError` back at the peer — exactly what the
malformed-envelope branch already does. Before item 3 was fixed, doing that to a peer running
this same codebase would have *crashed them*. Fixed in the same plan, in that order, the two
compose: the rejected peer ends its own game cleanly instead. This is why both items belong in
one plan rather than being split.
