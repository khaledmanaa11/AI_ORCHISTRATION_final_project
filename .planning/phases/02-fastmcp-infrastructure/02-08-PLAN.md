<objective>
Build the game-start handshake: a single exchange that proves the opponent is reachable **and**
verifies the two sides are playing by the same numbers, aborting the game **before move 1** if
they are not (D-08, D-15 — NET-03, NET-05, NET-09).

Purpose: `docs/RULES.md` rule 11 makes "verify the configuration file is identical byte-for-byte
on both sides" a **MUST**, sanctioned by game disqualification for a symmetry breach. D-15 fixes
where that verification happens and what it costs when it fails: a SHA-256 of `game_params.json`
is exchanged during the handshake, and **any** mismatch aborts before the first move. Not a
warning. Not a soft-fail that plays on with a note in the log. A game played on divergent rules
produces a result neither side can defend, so the only correct behaviour is to not start.

Two properties make this module harder than it looks, and both are locked here rather than left
to the executor:

1. **Reachability failure and digest mismatch must never be confused.** The two agents start in
   two terminals at slightly different times, so the first one ready will find the other not yet
   listening. That is a *transient* condition the caller should retry. A digest mismatch is
   *permanent* — retrying cannot make two different configs agree. Collapsing them into one
   "handshake failed" path either spuriously aborts a legal game or, far worse, retries past a
   real config divergence and plays it. So `UNREACHABLE` leaves the machine playable and returns
   for the caller to retry; `CONFIG_MISMATCH` escalates to `State.ERROR` and ends it.

2. **The handshake is symmetric (NET-03).** Neither peer is authoritative, so *both* verify. The
   responder checks the incoming digest against its own and escalates its own machine — it does
   not wait to be told. And it **still replies with its own digest even while aborting**: raising
   from the tool body would reach the initiator as a tool-side error and be misread as anything
   other than what it is. Both sides must be able to write the same truthful evidence.

Scope discipline: this module makes **one** attempt per call. The retry budget and the response
deadline belong to 02-07's deadline module and are wired by 02-09 — so no timeout, retry count or
backoff value appears in this file, and 02-08 does not depend on 02-07. Phase 6 later adds the
Step-0 declaration to this same handshake; the envelope payload is a dict precisely so that is an
additive change. **Do not add Step-0, nonces, or commitments now.**

<design_notes>
<!-- Decisions made inside this plan's delegated discretion (CONTEXT.md: "module layout, naming, -->
<!-- and file split"; "test structure and mocking approach"). State them in the SUMMARY.       -->

1. **The peer call is injected, not imported.** `perform_handshake` takes a `HandshakeCaller`
   rather than a `PeerRuntime` or a `Client`. Three reasons: (a) it keeps the retry/backoff budget
   in 02-07 where D-13 put it, so 02-09 can wrap the caller in `call_with_retry` without this
   module knowing anything about retries; (b) it means 02-08 needs no dependency on 02-07;
   (c) the failure paths are testable with a three-line fake instead of a network. The
   `make_client_caller` adapter is the bridge to 02-06 for 02-09's benefit.

2. **One attempt per call — the waiting budget is not ours.** No `asyncio.sleep`, no loop, no
   `wait_for`, no timeout argument anywhere in handshake.py. Startup skew is handled by the
   caller retrying an `UNREACHABLE` result, using 02-07's config-sourced retry count and backoff.
   This is also why `UNREACHABLE` must not touch `State.ERROR`: escalating on the first missed
   connect would make the faster-starting agent abort a perfectly legal game.

3. **Transition first, then exchange.** `perform_handshake` calls `machine.attempt(State.HANDSHAKE)`
   before contacting the peer, so `State.HANDSHAKE` truthfully means "handshaking in progress". On
   a retry after `UNREACHABLE` the machine is already in `HANDSHAKE`, so the second attempt is the
   illegal self-transition `(HANDSHAKE, HANDSHAKE)` — which 02-03 classifies as **RECOVERABLE**
   (design note 3: duplicate/retry). That report is correct and wanted, not noise: NET-05 requires
   every such attempt to be visible. Guard the exchange on `machine.state is State.HANDSHAKE`
   after the attempt, and return early (no peer call) if the machine landed anywhere else.

4. **The responder replies even while aborting.** `respond_to_handshake` returns its digest in
   every case and never raises. If it raised on mismatch, FastMCP would surface a `ToolError` to
   the initiator, which by RESEARCH Pitfall 4 is a *different* failure class from a timeout — the
   initiator would record "the opponent's tool errored" instead of "our configs differ", and the
   two peers' logs would disagree about why the game did not start. Both sides must be able to
   write the same evidence, so the mismatch has to arrive as data.

5. **The single permitted numeric literal.** `HANDSHAKE_TURN = 0` is the structural index of "before
   move 1" — the same category as `turn=0` and `barriers_placed=0` in `sdk/engine.make_state`,
   which 01-04 accepted and pinned with an AST audit permitting only `0`. It is not a value from
   `docs/PARAMETERS.md` and not a tunable. Every other number this module could want (timeout,
   retries, backoff, port) is deliberately absent because it belongs to `NetworkParams` and to
   02-07. If the executor finds it needs any other number, it must stop and add an `## OPEN`
   section to the SUMMARY rather than choosing one.

6. **Neither side is named as the wrong one.** The mismatch `detail` and the reporter `reason`
   state both digests and nothing more. Writing "the opponent's config is wrong" would be an
   unfounded declaration — this peer cannot know which config is the correct one, and
   `docs/RULES.md` forbids untrue declarations. Format:
   `"config digest mismatch: local=<hex> remote=<hex>; aborting before move 1 (rule 11, D-15)"`.

7. **Role strings come from `role.json`, not from this module.** `local_role` is a parameter.
   `config/police/role.json` is `{"role": "police"}` and `config/thief/role.json` is
   `{"role": "thief"}`; 02-09 reads them. handshake.py never hardcodes a role name, and never
   branches on one — the protocol is symmetric.
</design_notes>
