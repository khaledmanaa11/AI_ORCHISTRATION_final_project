<objective>
The phase's headline deliverable: the brain that chooses moves from the trained table, and
knows when not to trust it.

The subtle requirement here is STRAT-02's trigger. Acting on any key present in the table is
the obvious implementation and it is wrong — a key visited twice holds noise, and a policy that
acts on it looks trained while playing worse than the plain heuristic (AI-SPEC critical failure
mode 2). The trigger is a **visit count** threshold, and the boundary is tested explicitly
because "100% of decisions below the threshold are served by the fallback" is a Critical eval
dimension (E3), not a nicety.

The second requirement is provenance. `Decision.source` must be truthful on every move, because
E2 replays each move against its declared source, and because rule 25 makes an
LLM-or-anything-else-chosen move a disqualification.

Output: `src/pursuit/strategy/qlearning.py`, registered in the registry, plus its tests.
Training that fills the table is 03-08; this plan consumes a table, it does not produce one.
</objective>

    Tests first. Then `QLearningBrain(BrainBase)`:

    - Constructor takes `StrategyParams`, a role, and an injected `random.Random`. It loads the
      Q-table from `qtable_path` **once, here**. No file I/O anywhere in `_pick_move` (E11).
      A missing table file at construction is a loud failure, not a silent empty table — the
      shipped agent must not quietly play at random in a league game.
    - `_pick_move(obs)`:
        key = encode_state(obs, params)
        if table.visits(key) < min_visits:  -> fallback.pick(...), source=FALLBACK
        else with probability epsilon       -> explore via the injected rng, source=QTABLE
        else                                -> table.best_action(key), source=QTABLE
      `epsilon` comes from config; match/eval play uses `epsilon_eval` (0.0), so shipped play is
      greedy and reproducible.
    - `_decide_move(obs)` returns the movement plus `barrier=None` for now, with a `# 03-07`
      marker where the cop's barrier sub-policy attaches (D-12 — the action space stays at 5).
    - `update(prev_key, action, reward, next_key)` applies the §5 rule and bumps the visit
      count. Keep it a plain method on the brain so 03-08's harness drives it without reaching
      into the table directly.
    - Instance state only; no module-level mutables (D-03).

    Register the class in `registry.py` under the config name.

    If the module approaches 150 lines, split selection from the update rule into a sibling

  <files>tests/unit/strategy/test_qlearning.py</files>

  <action>
    Build a synthetic `QTable` fixture with visit counts swept across the threshold, then cover:

    1. **Above threshold** — a key with `visits == min_visits` and a clear argmax returns that
       action with `source == QTABLE`.
    2. **Below threshold** — `visits == min_visits - 1` is served by the fallback with
       `source == FALLBACK`, even though the key exists in the table with a strong value. This
       is the test that distinguishes the correct trigger from the naive key-presence one.
    3. **Absent key** — served by the fallback.
    4. **Boundary sweep** — parametrized over visits from 0 to `min_visits + 2`, asserting the
       routing is correct at every point (E3 demands 100%, so test the whole neighbourhood).
    5. **Exploration is seeded** — two brains constructed with `random.Random(same_seed)`
       produce identical move sequences; different seeds diverge. Confirms D-19 and makes
       training reproducible.
    6. **Greedy at eval** — with `epsilon_eval = 0.0` the brain never explores; run enough
       decisions that a nonzero epsilon would almost surely show.
    7. **Update rule** — one `update()` call moves the Q-value by exactly
       `alpha * (r + gamma * max_next - old)`, computed independently in the test, and bumps
       visits by one.
    8. **No I/O on the decision path** — patch `open` (or `pathlib.Path.read_text`) to raise,
       then call `_pick_move` and assert it still works (E11).
    9. **No cross-role state** — a cop brain and a thief brain built from the same config share
       no mutable object; mutating one's table leaves the other's untouched (rule 2).
  </action>
  <verify>
    All nine pass. Deliberately weakening the trigger to `key in table` makes test 2 and part of
    test 4 fail (confirm, then revert).
