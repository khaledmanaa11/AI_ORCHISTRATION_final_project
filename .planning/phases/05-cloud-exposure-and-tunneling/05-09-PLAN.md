    clause to `except (ToolError, httpx.LocalProtocolError, httpx.UnsupportedProtocol): raise`.
    No catch-all is added; verification item 6 greps for one.

    Subtract-by-raise-first, not by narrowing the tuple: that keeps any FUTURE httpx addition
    under `TransportError` retryable by default — the right default for a transport family —
    while naming the two local-fault classes explicitly.

    Extend the module docstring's taxonomy paragraph with the reasoning, which is the
    load-bearing part of this task:
      - `httpx.TransportError` is the connection/read failure family — the same failure class
        `McpError` already covers, arriving by a different library's exception tree because
        fastmcp's client raises httpx's errors directly on the connect path. Members kept
        retryable, with the reason: `ConnectError`/`ReadError`/`WriteError`/`CloseError` and
        the four `TimeoutException` members are transient by definition; `PoolTimeout` is our
        own exhaustion but is transient and a backoff is exactly right (and nearly
        unreachable here — every call site opens a fresh `async with ctx.runtime.client()`);
        `RemoteProtocolError` most commonly means "server disconnected without sending a
        complete response", which is the 2026-08-13 shape itself, and a genuine
        application-level rejection arrives as `ToolError` instead.
      - `httpx.LocalProtocolError` and `httpx.UnsupportedProtocol` are RAISED, not retried:
        both mean the fault is ours and is deterministic, so all four attempts fail
        identically and the ladder ends in a durable `TechnicalWin(OPPONENT_UNRESPONSIVE)`
        against a peer that never received a valid request. State plainly in the docstring
        that re-raising these is NOT a reintroduction of the crash this change exists to fix:
        a scheme-less `PURSUIT_OPPONENT_URL` is a configuration error that fires at handshake
        before any game exists, and failing loudly on bad config is this codebase's house
        style (`load_network_config` already raises) — strictly better than ~135 s of futile
        retries ending in a false accusation.
      - `httpx.HTTPError` is DELIBERATELY not used: `HTTPStatusError` is a sibling under it,
        and a 403 from `SharedSecretMiddleware` is an application-level answer about our own
        credentials. Cite `tests/integration/test_secret_channel.py::test_wrong_secret_fails_every_call`
        as the live anchor — it drives the real fastmcp client over a real socket and asserts
        `httpx.HTTPStatusError` with "403", proving this is not an MRO argument.
      Verify the hierarchy yourself before writing any of it — do not take the plan's word.

    `tests/unit/test_deadline.py`: add cases proving a `ConnectError` is retried through the
    ladder and yields a TechnicalWin with measured evidence on exhaustion; that
    `TechnicalWin.last_error` carries the real exception text (`call_with_retry` already sets
    `f"{type(exc).__name__}: {exc}"`, so the artifact a grader reads says
    `ConnectError: All connection attempts failed` rather than a bare accusation); the CONTROL

    re-raised, burns no backoff, and produces no TechnicalWin. Existing cases stay unmodified
